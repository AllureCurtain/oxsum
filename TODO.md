- 2026-10-03 The generative oracle reads a settlement's hold from the ledger (issue #41), which is what turned CI red on `main` after B-10 and left B-10's "CI is green on a fresh clone" unmet. `Case::check` applied a written settlement as `reserved -= request.held`, and a settlement built while the key it names held nothing carries the placeholder `ONE` in that field: a hold refused for insufficient funds leaves its key free, so a collision can write a hold there afterwards, and a replay of the earlier settlement then succeeds — the wallet released the entry's amount while the model subtracted the placeholder, which is exactly the `after op 5: Replay { which: 3 }` failure CI reported (`911_018 = 1_911_018 - 1_000_000`). Pinned by `a_settlement_releases_the_hold_the_ledger_holds`, a deterministic case on a ledger of its own — proptest's persisted seed carries the sequence but not the carry-over balance the failing run happened to have, so replaying that seed against a fresh database passes. - 2026-10-03 Per-key spend limits (issue #32): `oxsum.api_keys.spend_limit_minor` (nullable, minor units; NULL is unlimited) caps a key's committed spend — settled charges plus outstanding holds attributed to it. Attribution rides on the hold entry's `provenance.actor` (the key id); `Wallet::settle` copies it onto the settlement entry, so releases and charges attribute with no extra plumbing. Enforcement is `Wallet::hold_for_key`: a per-key advisory lock, a re-read of the limit from the locked key row, a committed-spend read from the ledger, then the engine's normal append — the lock is held until commit, after the append, so racing holds cannot both pass the check and the vendored engine is untouched. Over the limit is 429 `KEY_LIMIT_EXCEEDED` on `/api/v1` and `insufficient_quota` on the gateway; `spendLimitMinor` is set at key creation or via `PATCH /api/v1/org/keys/{keyId}` under the revoke scope rules; sessions carry no limit. Covered by `crates/core/tests/key_limits.rs` (the limit, settled spend counting, ten racing holds against one limit with exactly three succeeding, limit changes applying to later holds, scope rules) and `crates/server/tests` (contract round-trip, the 429s, a session hold unbounded by key limits); openapi.yaml is at 0.7.0; the decision is recorded in docs/decisions.md.

- 2026-10-03 Trustworthy tree heads (issue #30): the operator signs each tenant's ledger head as a C2SP `signed-note` (a `tlog-checkpoint` body) with an Ed25519 operator note signature under the fixed key name `oxsum/tree-heads`, using doubleentry's witness module as a dependency — `crates/doubleentry` itself is untouched, only the `witness` cargo feature is enabled on the workspace dependency. Origins name the tenant ledger (`oxsum/ledgers/<tenant_id>`); signing is on demand and stateless, so there is no heads table to drift and no migration on key rotation. Three endpoints (openapi.yaml 0.6.0): `GET /api/v1/log/head` (the signed current head), `GET /api/v1/log/consistency?from=` (the signed new head, the old head recomputed from the log, and the proof between them), and the public `GET /api/v1/log/key` (key name, base64 public key, signature selector). `from=0` is 400 — a proof from the empty tree would verify against any history. The seed is `OXSUM_HEAD_SIGNING_KEY` (32 bytes, base64, in `.env.example`); without it the log surface answers 503 `SERVICE_UNAVAILABLE` while the wallet serves on. There is deliberately no server-side `Witness`: the operator witnessing its own log proves nothing, and the C2SP wire format is what lets third-party witnesses cosign later. Covered by `crates/core/src/heads.rs` unit tests (sign/verify round trip against the published key, tamper refusal) and `crates/server/tests/heads.rs` (the full user flow: hold an old head, grow the log, verify the new head was appended onto it; the refusal cases; per-organization origins; the 503s); the decision is recorded in docs/decisions.md.

- 2026-10-03 Web login (issue #17): a session is a second credential next to the API key. `POST /api/v1/auth/login` (email + password, argon2) mints a session and answers it in an `HttpOnly`, `SameSite=Lax` cookie (`oxsum_session`, `Secure` when `OXSUM_SESSION_COOKIE_SECURE` is set); `GET /api/v1/session` names the user, the organization and the role; `POST /api/v1/auth/logout` revokes the session, clears the cookie and always answers 200. The cookie value is `oxsess-` plus 32 random bytes and the database keeps only its SHA-256 hash, so a dump of `oxsum.sessions` authenticates nothing. Resolution joins `memberships`, so a session dies with its membership; expiry is thirty days absolute. An unknown email and a wrong password answer the same 401 with the same message, the unknown-email path still paying for one hash verification. Role checks live in core: members list and revoke only the keys they created (anything else is 404, the key stays live), owners/admins see and revoke all, and a key acting as the organization keeps its pre-session authority — roles constrain sessions, not keys. Keys minted through a session carry `createdBy`; keys minted with an API key keep it null. The cookie is never accepted on `/v1`. Covered by `crates/core/tests/sessions.rs` and `crates/server/tests/sessions.rs`; `openapi.yaml` is at 0.5.0 with the three endpoints and the `sessionCookie` scheme; the decision is recorded in docs/decisions.md ("roles constrain sessions, not keys", Lax plus JSON). - 2026-10-03 Settlement-hold pairing (issue #10): a settlement now names the hold it releases (`holdKey`); the server reads the hold's amount from the hold entry in the ledger, so the request carries no amount to assert. - 2026-10-02 The gateway loop: `POST /v1/chat/completions` and `GET /v1/models` relay to one configured upstream, freezing an upper bound from the request text and the output ceiling *before* the call and settling against upstream's usage afterwards. The freeze, the priced usage, the local estimate and the settlement record are all arithmetic in `crates/core/src/billing.rs`; the relay is an `async-stream` generator that forwards upstream's frames, reads the usage out of the last one, and awaits the settlement before it ends, so a finished stream is a settled bill. The write itself runs in a task of its own, because an OpenAI SDK client hangs up the moment it reads the terminator — which over a real socket lands while the entry is being appended, and an append cancelled there used to leave the freeze reserved with nothing left to release it. A client that does cut a turn short cancels the upstream call and settles what had been forwarded as `client_cancelled`, from upstream's counts when it had already reported them; an upstream error or an unreachable upstream charges nothing and releases the freeze whole; usage above the freeze is charged at the freeze and recorded as `capped`. Every response carries `x-oxsum-request-id`, and `req-<id>:hold` / `req-<id>:settle` are the entries it wrote. `crates/server/tests/gateway.rs` runs a scripted upstream in-process and covers all of it, and the loop was driven by the official OpenAI Python SDK against a mock provider with nothing but `base_url` changed — its streaming call is what exposed the cancelled append.
