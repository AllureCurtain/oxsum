# T29 — Release artifact and candidate gates

- Issue: [#620](https://github.com/AllureCurtain/oxsum/issues/620). Scenario: A30 (candidate artifact).
- Candidate branch `feat/release-gates`; commit recorded in the PR. Base: `cad53b8` (PR #672 merge).
- Environment: `local-isolated`, macOS arm64, Docker Desktop (Compose v5), Rust stable + `wasm32-unknown-unknown`, wasm-bindgen-cli 0.2.129 (Cargo.lock's version), Node 22.

## What the gate is

`.github/workflows/release-candidate.yml` (`workflow_dispatch` +
`workflow_call`, one input: `sha`) runs on the exact promoted commit —
the `resolve` job refuses a SHA that is not an ancestor of main, and every
job checks out `needs.resolve.outputs.sha` explicitly.

| Job | What it does on the promoted SHA |
| --- | --- |
| `resolve` | validates the SHA is a commit and `git merge-base --is-ancestor` of `origin/main`; emits the resolved 40-char commit |
| `fmt` / `clippy` / `test` | `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -D warnings`, `cargo test --workspace --lib` + `--doc` — the fast gate tier |
| `wasm` | `scripts/build-verify-wasm.sh` with wasm-bindgen-cli pinned to the lockfile version; uploads `verify-wasm` |
| `frontend` | `npm ci` + `npm run codegen` + `npm run build`; uploads `web-dist` |
| `verify-consumer` | `scripts/check-verify-consumer.sh` — packs `verify-oxsum-bill`, installs into a clean project, verifies the genuine v2 bundle and rejects tampered/dropped/wrong-org; uploads the exact tarball as `verify-oxsum-bill-tarball` |
| `examples` | `scripts/verify-examples.sh` — the T26 developer examples end to end on a fresh scratch deployment (postgres service + server built at the promoted SHA); the A27 fresh-install gate |
| `image` | full Dockerfile build with `GIT_SHA=<sha>`, `load: true`, **no registry login and no push**; records the image identity |
| `manifest` | `candidate-manifest.json` (SHA, run URL, image identity, per-gate verdicts), `SHA256SUMS` over all artifacts, `RELEASE-NOTES-DRAFT.md` cut from the SHA's own `openapi.yaml` changelog paragraph; all uploaded as `candidate-bundle` (90 days) |

The heavy tier (three nextest shards + process-shared suites + doubleentry
Postgres conformance) is **not** duplicated: a promoted SHA is a main
commit, so ci.yml's post-merge push run already covered it — the runbook
(`docs/self-hosted-release.md`) names that run gate 0. A displaced push's
missing gate is re-verified by the nightly or a ci.yml re-dispatch.

`scripts/release-candidate-smoke.sh` is the operator-run gate 2: throwaway
compose project + volume + generated secrets, then `--check-config` →
`--migrate-only` → `/readyz`/`/healthz`/`/api/v1/version` → T03 setup flow
(setup-token mint → owner register → login → explicit business-context
switch → `GET /api/v1/business`) → staff customer invitation →
`check-verify-consumer.sh`; full teardown on exit, any pre-existing
`deploy/.env` restored untouched. It never touches a production deployment.

The smoke script's live half (steps 1–5 against a real compose stack) was
syntax-checked and its env/compose resolution verified, but not run end to
end here — it needs a local image build (~minutes) and is the operator's
gate-2 step; its exact behavior is documented in
`docs/self-hosted-release.md` and the script's own step banner.

## A30 mapping

| A30 requirement | Coverage |
| --- | --- |
| Same-SHA image + full gates | `resolve` pins the SHA; fast tier + wasm + frontend + image run on it; gate 0 = main post-merge heavy tier |
| Startup / version / readiness | smoke steps 1–3 (`--check-config`, `--migrate-only`, `/readyz`, `/api/v1/version` gitSha) |
| Customer + business surfaces | smoke steps 4–5 (setup flow → `/api/v1/business`; staff `customer-invitations` write) |
| Browser verifier positive + negative | `verify-consumer` job + smoke step 6 — verified locally above |
| Clean consumer of the packed artifact | the exact `.tgz` the consumer installed uploads as `verify-oxsum-bill-tarball` |
| Checksums / provenance / notes | `candidate-bundle`: `SHA256SUMS`, `candidate-manifest.json`, `RELEASE-NOTES-DRAFT.md` |
| No publication claim | no registry login, `push: false`, no npm publish, no deploy trigger — the workflow is structurally unable to publish |

## What T30 needs from this seam

- `release-candidate.yml` is the candidate gate; `candidate-bundle` (manifest
  + SHA256SUMS + notes draft + all artifacts) is what a T30 review reads.
- `scripts/release-candidate-smoke.sh` is the repeatable live-smoke; T30's
  integrated acceptance can run it against the T29-gated image verbatim.
- `docs/self-hosted-release.md` is the gate-order runbook T30's release
  checklist should cite.
- T26's `scripts/verify-examples.sh` runs inside the gate as the `examples`
  job — no follow-up needed; A27's fresh-install half is covered on the
  promoted SHA.
