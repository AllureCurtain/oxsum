## Implemented and observed

Deployment authority mints a random 256-bit token bound to an intended owner email, valid 30 minutes. Only its hash persists. Same mint key/terms returns metadata with null token; changed owner conflicts. Existing-owner acceptance requires a live personal session for the invited email; customer API keys and other sessions cannot substitute. New-owner registration reuses the signup transaction helper and creates the personal customer identity/key without opening a ledger.

The singleton lock serializes initialization. Setup token consumption, new account (where needed), staff ownership, initialized profile and redacted audit commit together. Concurrent acceptance yields exactly one owner. Restart and rerun preserve initialization; no further token can be minted. Database triggers refuse changes to setup authorization/initialization audit rows.

Fault injection raises an error at the final audit insert after account/staff writes. The transaction leaves zero users/staff/accepted tokens and null initialization; removing the test fault permits the original token to succeed. No test edits a ledger table. The genuine legacy ownership fixture still preserves keys, statements, balance and signed evidence.
