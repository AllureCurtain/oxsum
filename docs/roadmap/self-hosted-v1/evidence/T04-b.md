## Behavior and boundaries

Business owner/admin invitations reserve the intended customer's UUID, external ID, name and email for seven days. Acceptance creates the customer/profile and first owner atomically. Existing users retain their original organization, keys and selected context. New-user redemption creates the account and first key, with no staff or funding grant. Team invitations grant only member, with explicit logged-in acceptance for existing users. `POST /org/members` is retired before body parsing; the old public core direct-add operation is removed, with crate-private provisioning retained only for demo seeding.

Creation/revocation use immutable scoped idempotency receipts; the token itself makes acceptance replay-safe. Only first creation returns the secret; replay returns null and does not resend email. Tokens are hashed. Repeated acceptance never restores a removed membership. Current personal session, TOTP and manager role are read inside mutation transactions. Audit, membership, profile, key and invitation state roll back together. Legacy unspent invitation IDs/hashes/expiry survive migration 0076. No ledger engine edit.
