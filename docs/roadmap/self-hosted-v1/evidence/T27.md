## Measured results

Hardware/Postgres declared above; workload = the suite's own fixtures, not the full D09 1,000-customer target — see *Residue*.

- **Schema count** (`scripts/measure-schema-count.sh`, dev cluster, 2 tenant schemas): each `ledger_<tenant>` schema carries **11 tables + 26 indexes**, ~424–920 kB heap. The `oxsum` schema carries 110 tables + 268 indexes. At the D09 1,000-customer shape the projected tenant overhead is ~11 k tables / 26 k indexes of catalog rows — a count to watch, not yet a measured limit.
- **Busy-customer fairness**: one tenant at 12 concurrent holds beside a second at serial holds. Quiet-tenant hold p99 went from **12.9 ms baseline to 259.6 ms contended** (~20×). The bound the cell asserts is an absolute sub-second ceiling — the shape a true lock/pool serialization across tenants would blow past (seconds, not tens of ms). 259 ms is pool-checkout queueing on the shared 16-connection pool, the documented shared-pool cost, not starvation.
- **Pool exhaustion**: saturating all 16 connections makes the next `available()` surface `PoolBusy` in ~30 s — the configured `acquire_timeout` — and recovers on release. The bound is explicit backpressure, not a hang.
- **Process caches**: `RouteStats` caps at 256 channels, `Affinity` at 8 192 sticks, `Tenants` holds one shared `Arc<Wallet>` per distinct tenant.

## Bugs found and fixed

One, in the harness — not the code: the promo pin/expiry assertion `remaining_minor ∈ [0, grant]` was too strict, because a reserved draw's accounting sits in `reserved_minor` beside `remaining_minor`. The corrected invariant is conservation — `remaining + reserved ≤ grant` and `remaining ≥ 0` — which holds under every race order. No production bug surfaced; every cell's invariant already holds on main.

A test-side note on environment: the shared `.worktrees/target` can serve a stale `oxsum-core` rmeta when a sibling worktree's `cargo check` runs an older source under a matching fingerprint — the failure shows as "method not found" for a function that exists. The suite runs clean under an isolated `CARGO_TARGET_DIR`; on the shared target, delete the matching `liboxsum_core-*.rmeta`/`rlib` when a sibling build interleaves.

## Residue and what T30 needs

- The D09 target (1,000 customers, 10,000 keys, 100 concurrent streams, ≥20 ops/s, p95 gateway overhead <100 ms on 4 vCPU/8 GiB) is **not fully measured here**: the cells and regression run on a development Postgres, and the workload is the suite's fixtures, not the normalized 1,000-account shape. The schema-count, fairness and cache-bound cells give the per-unit figures T30 scales; a dedicated D09 load run against declared infrastructure remains the gap T30 must close or explicitly scope as a release limitation.
- The 5-minute soak (`scripts/soak.sh`) is written and drives a live deployment over the public API; it was not run to completion against a production-representative deployment here — the local compose stack is the fixture, not the target hardware.
- `route authority` coverage is structural (mounted-set ≡ classified-set) plus a 14-probe key-denial walk; it does not re-walk every route under every role — the per-role matrix already lives in `financial_authority.rs`/`consumption_scope.rs`.
- Known shared-target hazard: serialize heavy cargo/nextest across worktrees, or run this suite under an isolated `CARGO_TARGET_DIR` when a sibling build is mid-flight.
