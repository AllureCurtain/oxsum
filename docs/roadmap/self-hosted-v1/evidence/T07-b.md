## Behavior and review

`ResponseCacheContext` replaces the retired normalized-prompt digest. A cache lookup now fingerprints one canonical value built from the exact caller body, the exact body that would be forwarded upstream (model, alias target, output bound), concrete upstream endpoint plus protocol-owned semantic headers (`anthropic-version`, the forwarded `anthropic-beta`), the `ServingAccess` permission snapshot, the key's admission constraints, the selected experiment and mandate, the served and requested model names, every admitted route's channel/protocol/destination/settings/credential fingerprint/weight/configuration generation/price version/price, the fallback names and alias targets and the discount.

Canonicalization sorts object keys only. Every array element, string byte, null and number is preserved, so text case and whitespace, tool definitions, media parameters and generation settings each produce a different key. The stored value is `v2:` plus HMAC-SHA256 under the deployment sealing key (`oxsum/response-cache/v2`); no prompt is persisted and a deployment without a sealing key cannot read or write the cache. Migration 0080 deletes pre-v2 rows: a cached answer is a rebuildable projection, and an incomplete key is not migrated across customers or contexts (D04).

Lookup remains organization-scoped and key-scoped through the permission snapshot. Sibling consumption keys, changed permissions, a repriced or repointed route, a different experiment/mandate or a changed fallback set cannot reuse an answer. `excludeSystem` remains in the contract for compatibility but is ignored: the system preamble is part of the question. The hit itself is unchanged — the stored body re-served at the cache-read rate with `similarity: 1.0`, `upstreamAttempts: 0` and the original source entry. Streaming, non-provider-reported usage and non-primary-route answers are still never stored. A primary route with no available credential cannot answer from cache. Credential configuration fingerprints include every configured ID, ciphertext, position and status inside a keyed digest, exclude runtime health timestamps, and never expose secrets. They are read in the same repeatable-read snapshot as the route.

## Review corrections

The prior candidate used only the protocol label (`openai`) rather than the concrete endpoint; identical admitted bodies could collide between Chat and Responses. It also used a channel timestamp that credential-pool changes did not advance, retained only fallback names, and did not register migration 0080 in the explicit migration runner. The revised implementation binds the concrete endpoint, all route/alias/configuration identities and a private credential-configuration fingerprint, requires an available primary credential for cache eligibility, and registers the migration. HTTP regressions exercise endpoint collisions, add/disable/remove credential invalidation, fallback target/configuration changes, changed permissions and denial; upgrade coverage verifies stale rows are actually deleted without touching ledger history. Existing preliminary green tests are not treated as final validation for these corrections.
