# Architecture

Business setup readiness (#843) lives in `crates/core/src/business_readiness.rs`.
The HTTP adapter passes only the current personal token, the process encryption
key and public-return-URL presence. The business-locked transaction rechecks current
authority after acquiring the lock, serializes with configuration changes and derives
five actor-scoped facts without writes or external probes. Provider credential
health uses the gateway's pool filter; alias shadowing follows the catalog;
default sale terms must be effective and match usable chat supply. Collection
requires the owner's explicit route, enabled current merchant credentials and
the existing collection-terms validator. The frontend renders restricted/error
states explicitly. Customer readiness remains separate because its key grants,
funding and first-call proof have different authority and evidence.

## Self-hosted release target

The accepted [design](roadmap/self-hosted-v1/DESIGN.md) (#591) retains existing Organization IDs, tenant schemas and proofs as customer billing accounts and adds separate Business ownership/staff scope. There is no second commercial wallet or project wholesale charge. Durable single-customer operations coordinate financial and entitlement effects; sale prices remain independent of provider expense. These changes are planned until their [implementation issues](roadmap/self-hosted-v1/STATUS.md) integrate. [Baseline reconciliation](roadmap/self-hosted-v1/BASELINE.md) records the current source and compatibility boundaries.


## Overview

```
Browser ──→ React dashboard /app (Vite build, rust-embed'd)         │
          ──→ /verify, server-rendered skeleton + wasm verifier (Topcoat) │
LLM clients ──→ Gateway /v1/chat/completions, /v1/messages, ───────┤  one process, one binary
                /v1/embeddings, /v1/rerank                          │
API callers ──→ axum /api/v1 ──────────────────────────────────────┤
                                                                   ▼
                     oxsum-core (Wallet / Tenants / Db)  ──→ upstream LLM (gateway relay)
                                                                   ▼
                     doubleentry (bookkeeping, Merkle log)
                                                                   ▼
                     PostgreSQL: one ledger schema per organization, plus one `oxsum` schema
                     holding users, organizations, memberships and API keys
```

The axum API, the core, doubleentry and the gateway exist today, with oxsum's own identity tables in one `oxsum` schema. The user-facing dashboard is the React app under `web/` — built once, embedded into the binary and served at `/app` (issue #234); it reached parity and the server-rendered Topcoat pages retired to it (issue #256), so the legacy page paths now `301` to their `/app` twins and only the public `/verify` check stays server-rendered.

`Db::diagnostic_snapshot` reads only fixed schema/queue/configuration aggregates in a repeatable-read, read-only transaction. The operator-guarded HTTP endpoint adds parsed configuration presence and a six-second deadline; `scripts/operator-diagnostics.py` accepts only allowlisted response fields and optional explicit local env presence. It never reads ledger amounts, copies error bodies, claims jobs or probes external providers. [Diagnostics](operator-diagnostics.md) documents the boundaries.

| Gateway | `crates/server/src/gateway/` | The `/v1` surface: model list, `chat/completions` in OpenAI's shapes, `messages` in Anthropic's, the input-only `embeddings`/`rerank` surfaces in OpenAI's, and `responses` under the same `openai` protocol — each surface serves only the channels that declare its protocol *and* price the model under the surface's billing mode, and errors come back in the shape that surface's SDK parses. The relay that freezes before upstream and settles however the turn ends is shared by all four. Its own auth middleware, because a refusal here has to look like the client's own protocol's. It resolves the model's routes from the rows in `crates/core` once per request — one per channel, each a `(channel, version, weight, price)` plus the channel's healthy credentials — orders them with a weighted pick followed by descending weight (`route_order_stats`, cost-aware inside an equal weight tier since #438, health-aware since #499 — a process-local `RouteStats` EMA of time-to-first-byte and error rate scales each serving's effective weight, so a slow-but-alive channel counts as a fraction and an erroring one is dropped for a 60 s cool-down, the stats a routing hint on `Db`, never a billing fact), and freezes the dearest candidate's bound so whichever route answers stays inside the hold. A key's request group narrows the resolved serving candidates at admission, before routing, cache lookup and fallback. Ungrouped keys retain access to all channels; a group with no channels denies all. The admission snapshot remains in force for the in-flight request. A refusal before the first answer byte (unreachable, 429, 5xx) rotates to the next attempt — the picked channel's own credential pool first (issue #444: a credential-produced 429/5xx cools that key for a bounded minute while the turn retries on the pool's next key, same model same price), then the next route; a last route's 429 naming a short `Retry-After` is waited out once; a refusal after bytes flow is never retried. When every route of the requested model is exhausted the request may fall to a configured fallback model (issue #500): `oxsum.model_fallbacks` holds the ordered chain per model — mutable config replaced atomically, not ledger, because `channel_prices` is append-only — and the attempt loop walks the flattened `(model, route, credential)` triples, re-judging the key's allowlist, a mandate's `models` and the tier's allowlist for each fallback name (a denied model is skipped, never a refusal). The freeze bounds the dearest serving across the whole chain. The settlement records the answering channel and version plus `upstreamAttempts` (description v5) and, from v12, `requestedModel`/`servedModel` — which credential inside the channel answered stays operational detail, never a billing input — which credential inside the channel answered stays operational detail, never a billing input, and the surface's `(protocol, endpoint)` pair resolves into the `UsageAdapter` that reads its usage reports — `embeddings` reads `usage.prompt_tokens`, `rerank` reads `usage.total_tokens`. Principle: **domain logic belongs in core; the gateway does protocol and orchestration only; server only assembles**. The litmus test — if the logic survives replacing the axum layer, it is in the right place. That is why the gateway is a module of the server crate rather than a crate of its own: everything it does is HTTP — routing, an OpenAI-shaped error body, request deserialization, and a relay whose lifetime is the response body's — while every number it charges by is computed in `crates/core/src/billing.rs` and every row it charges by is read through `crates/core/src/channels.rs`. Migrations follow the crate that owns the table (core's tables in `core/migrations/`), applied in dependency order at startup.

## Frontend/backend boundary

- External callers use REST/JSON; the contract is `crates/server/openapi.yaml`.
- The dashboard is a single-page React app (`web/`) served at `/app`; it talks to `/api/v1` in the browser, with no server-side page handlers. The bills export (`GET /dashboard/bills/export.csv` and `.json`) stays a server route — a download is a response, not a page — and the platform-admin pages call `/api/v1/admin/*` straight from the browser with the operator token, because that bearer credential is the deployment's and no session could hold it (docs/decisions.md).
- The one page still server-rendered is `/verify` (in `crates/web`): the skeleton is a plain form whose `verify.js` loader runs the `oxsum_verify` wasm build in the browser when the bundle ships (issue #284) — the verifier's bytes travel to the client rather than the client trusting a verdict the server rendered — and the form's native POST runs the same `oxsum_verify` on the server as the no-JavaScript floor. `crates/verify` is wasm32-clean by design (uuid's wasm32 randomness solved with the `js` feature, see docs/decisions.md); its `wasm` feature exports the `verify_*` functions over wasm-bindgen, and `scripts/build-verify-wasm.sh` produces the bundle `crates/web` embeds — a build without the toolchain ships the committed placeholder and the page stays on the server path.

## Auth and permissions

- API: an organization's API key in `Authorization: Bearer oxs-…`, or a session cookie from web login — both resolved to a principal (the organization, or the user plus their role in it) by middleware; handlers read the principal from the request, never from the path. Neither credential's plaintext is stored: the database keeps SHA-256 hashes and display prefixes.
- Web login: self-built session table (token hash, user id, organization id, expiry, revocation), cookie with HttpOnly, SameSite=Lax, Secure when the deployment says so; password hashing with password-auth (argon2). A session dies with its membership. Rationale in docs/decisions.md.
- Role rules: members list and revoke only the keys they created (anything else is 404), owners and admins see and revoke all; roles constrain sessions, not keys. One exception, and it is deliberate: managing memberships needs a session in the owner or admin role, so a key is refused there even though it acts as the whole organization — a key is not a person and names no role (docs/decisions.md, "membership management is a person's action"). The member list itself stays readable by every member.
- Between tenants: physical isolation, one schema per tenant, no filter columns in queries. The connection layer shares one pool; `SET LOCAL search_path` at the start of each transaction picks the tenant schema (mechanism in docs/decisions.md). oxsum's own tables are not in those schemas: they are schema-qualified (`oxsum.users`) in the one `oxsum` schema, so nothing about a request's organization can change which identity rows a statement sees.
- Planned:
  - Last-used timestamps on API keys, see TODO.md.
  - See docs/decisions.md and TODO.md.

## Core data flows

### Billing for one streaming call

1. Before relaying an LLM request, `POST holds` freezes an upper bound.
   - The pool accounts book a debit in the pending layer, split promo → bonus → wallet → credit — `Equity:Promo` (the balance that can expire) funds what it can, `Equity:Bonus` next, `Liabilities:Wallet` carries what it can, and `Liabilities:CreditLine` carries the rest while undrawn credit remains; available balance drops accordingly.
   - All four pools carry a `FundedReservations` limit; the limit check and the write happen in one database transaction, with the pending layer included in the calculation, so concurrent holds cannot overdraw the pools or the credit line. A hold whose split a racing append invalidated retries with balances re-read rather than refusing a request the combined balance could have served.
   - The hold's promo share pins its funding lots in the same transaction (issue #609): `oxsum.promo_draws` records which `oxsum.promo_lots` rows, in expiry order — soonest-expiring first, never-expiring last — the hold's `remaining_minor` decrement went to, so a settlement debits the rows admission named rather than re-scanning.
   - A gateway request does this itself, before it opens the upstream connection: the freeze is computed in `crates/core/src/billing.rs` from the request text and the output ceiling, and its refusal is answered as OpenAI's 402.
   - Before the freeze, admission enforces the organization's tier (issue #158): the profile's model allowlist refuses a model it does not name (403), and its `requests_per_minute` spends one rolling-minute window keyed on the organization — shared by every key it owns — beside the key's own allowance below. The tier is never a pricing input.
   - Beside the price version, the turn also resolves its discount once at start (`Db::discount_percent`): the single most favorable `pricing_discounts` row matching the organization, the model and the moment. The snapshot rides the turn into the settlement, where it scales the summed numerator down by `percent` — one ceiling division — before the freeze's `min` applies.
   - Suspension gates the same point (issue #162): `organizations.suspended_at` is read inside `hold_for_key` and `hold` — every admission path shares them — under an org-scoped advisory lock the hold takes shared and `Db::set_suspended` takes exclusive, so a hold either observes the flag or committed before it. A suspended organization's in-flight holds still settle and money-in still lands: the flag writes nothing into the ledger. Suspending enqueues `org.suspended` for the organization's subscribed webhook endpoints in the flag's own transaction; a replayed flag emits nothing. The `statements` job's dunning sweep sets the same flag itself (issue #258): an opted-in organization (`dunning_grace_days`) whose finalized statement stands unpaid past `due_date + grace` is suspended with `dunning_suspended_at` marking the sweep as the suspender, and a later pass lifts a sweep-set suspension once nothing unpaid stands past grace — or when the grace is switched off — while a suspension the operator set by hand (`dunning_suspended_at` NULL) is never the sweep's to undo.
   - Key constraints are enforced inside `Wallet::hold_for_key`, in the transaction that holds the per-key advisory lock and the locked key row (issue #120): the model allowlist is checked against the model the gateway names, and the spend limit reads the constraint row in force — a `budget_duration` makes the committed read periodic, counting the current UTC window's settled charges plus every outstanding hold whatever its age. A replayed hold answers before either check, so a retry cannot be refused by a constraint that changed after its first landing. The wait for that per-key lock happens off the pool (issue #486): `hold_for_key` first queues on an in-process semaphore keyed by the same lock hash, so a hold that is only *waiting* holds no pooled connection — one busy key cannot starve the shared pool for every tenant — and a queue wait outlasting 5 s refuses `POOL_BUSY` like a saturated checkout.
   - A member's budget is checked in the same window (issue #162): `memberships.budget_limit_minor` — set on `PATCH /api/v1/org/members/{userId}` — caps the committed spend summed over every key `api_keys.created_by` attributes to the member. The membership row is locked for update inside the hold transaction, so two of the member's keys cannot both slip under the cap; the sum itself is the ledger's — settled charges plus outstanding holds, same provenance `key_committed_in` reads.
   - A team's budget sits between the member and the organization (issue #440): `oxsum.teams` (migration 0059) names a subgroup of members carrying `budget_limit_minor`, `memberships.team_id` assigns a member to at most one. When the minting member's team carries a cap, `team_committed_in` sums the committed spend across every key the team's members minted — the same postings read `member_committed_in` aggregates, grouped by roster — inside the same locked window, so a hold is refused `KEY_LIMIT_EXCEEDED` the moment `committed + minor` crosses it. The check orders key → member → team → organization credit line, each its own bound; a member with no `team_id` reads no team cap, and committed spend follows the roster — moving a member changes which cap their *next* hold sees, the money their keys already spent traveling with them.
   - A presented mandate's bounds run in the same window too (issue #262), after the key's own: the entry writes the mandate id as its provenance correlation, so `mandate_committed_in` sums settled charges plus outstanding holds under that id — the same postings sum, sliced by the delegation instead of the key. A settle copies the hold entry's correlation onto the charge the way it copies the actor, so the mandate's committed total stays ledger-derived across the hold → settle handoff and a racing second delegated hold cannot both fit.
2. When the stream ends, the settle is one transaction (issue #602, D05): the ledger entry — the release-and-charge for a held turn, the typed zero-cost receipt for a fully entitlement-funded one — the subscription draw's consumption, the winning attempt's usage, the operation's terminal row, the `oxsum.usage_records` row and the watch-row clear all commit or roll back together, so a crash mid-settle leaves no money moved without the operation that explains it. The ledger entry still does its two things:
   - Books a reversal in the pending layer, releasing each pool's slice of the hold
   - Charges actual usage in the settled layer, promo pool first, moving pools → revenue
   - The hold's pinned `promo_draws` close in the same transaction (issue #609): each draw's `charged_minor`/`released_minor` sum to its reservation, a released share returns to its lot while the lot is open — and burns `debit Equity:Promo / credit Equity:PromoExpiry` when the lot already closed, so expired promo never returns to refundable money.
   - A turn whose freeze the subscription covered whole holds no wallet reservation to release: `usage_receipt` writes a 1-minor balanced `Equity:Adjustments` marker carrying the same `Settlement` description, so the turn is recorded and provable while no balance, hold or revenue figure moves (issue #602).
   - The engine's part is `PostgresStore::append_in_tx`: the ordinary append — advisory lock, dense index, MMR nodes — run inside the caller's transaction, with `append` kept as the thin wrapper that opens and commits its own. The transaction's `search_path` pins the tenant's ledger schema for its whole life, because the schema's deferred balance trigger resolves names at COMMIT — see docs/decisions.md.
   - The same limit checks the release as a backstop, so the amount it gives back cannot exceed what holds reserved. The pairing itself is one-to-one: a settlement names the hold it releases, and the hold's entry is the amount — see docs/decisions.md.
   - The gateway settles when the relayed stream ends, and the settlement is awaited before the stream closes, so a client that read a stream to its end reads a settled bill. The write runs in a task of its own, so a client that hangs up while it is being appended cannot cancel it; a client that hangs up before that cancels the upstream call and settles what had been forwarded from a local estimate.
   - Inside the settle's transaction, the same path writes the turn's normalized usage row to `oxsum.usage_records` (`crates/core/src/usage.rs`, issue #102): the full dimensions pricing looks at, the caller's attribution, and `usage_details.provider_raw` — the mutable-store data an immutable entry description cannot hold. The entry stays the source of truth; a failed row write rolls the settlement back with it, and the sweeper retries what the turn could not finish.
   - After the settle commits, the turn also writes one `oxsum.request_log` row (issue #505): the per-request operational record a billing dispute or an SRE query actually reads — request id, the settlement `entry_id` it joins, requested and served model, channel, `admissionOutcome`, token counts, `ttft`/`total` latency, charge and `upstreamAttempts`. The write is deliberately *not* inside `record_usage_in`'s transaction — it rides beside the settle's success but free to fail, a logging failure traced and dropped, never a failed request (`crates/core/src/request_log.rs`). A request admission turned away before a hold logs a `refused` row off `record_refusal` — `admissionOutcome: refused`, zero charge, `error_kind` naming the cause — so the surface answers "which requests were turned away" without a ledger join. The retention job sweeps rows past `OXSUM_RETENTION_REQUEST_LOG_DAYS`.
   - The same write also rolls the turn into `oxsum.usage_daily` in the same transaction (issue #126): one row per `(tenant, booking day, key, channel, model)` sums turns, tokens and charge. The day key is the settlement entry's `booking_date` — the ledger's day, not the write's instant — so the rollup agrees with the statement period's seam. A replayed usage write inserts no row and rolls nothing; a usage row whose settlement entry is missing aggregates nothing and stays reconciler-visible drift.
   - The same write also refreshes the customer's **usage day log** (issue #337): one row per `(tenant, endUser, booking day)` holding the day's settlement count, the Merkle root over that day's settlement content hashes in log order, and the domain-tagged day leaf. The root is recomputed from the settled rows rather than appended incrementally, so it can never disagree with the rows it claims; a day with no settled usage has no row. A later stage anchors these leaves in the ledger and carries them in the report bundle, which is what turns "completeness is the organization's claim" into a proof (docs/decisions.md, 2026-10-22).
   - The same write also records `upstream_cost_minor` (issue #112): `Price::upstream_cost` resolves the same set the turn priced under and prices the usage at upstream's rates, so the row holds what the platform paid beside what it charged. The column is nullable by design — untracked, not zero, for a price without an `upstream` block, a swept turn, or history — and `Db::margin` sums the pair per `(channel, model)` for the admin margin view, counting the NULLs as `untrackedTurns`. Beside it `cost_basis` (issue #604, migration 0089) names how the figure was derived — `real_attempt`/`cache_reuse`/`estimate`/`missing`/`provider_reconciled` — so an allocation pass reads provenance directly rather than inferring it from `kind` and the NULL; a `cache_reuse` row made no upstream call (`upstream_attempts` 0), and a released or swept event is `missing`, never a fabricated zero. Upstream cost never enters a settlement description or an organization-facing endpoint.
3. Each step carries its own `idempotencyKey`, so retries are safe. For a gateway turn the hold's key is derived from the request id the response header carries (`req-<id>:hold`), and the settlement's key is derived from the hold's (`oxsum_core::settlement_key_for`).

### The hold sweeper

1. The gateway notes each hold in `oxsum.open_holds` *before* taking it, and deletes the row when the turn settles — however the turn ends, including the `Drop` path for a client that disconnects mid-stream. Historical raw holds retain their watch rows and remain sweepable; customer creation and settlement of raw holds are forbidden (#625). Their gateway context is empty, so a swept legacy hold remains an anomaly rather than a reconstructed turn. A row without a hold (the process died in between) heals itself: the sweeper deletes it when the hold is not there.
2. Every 60 seconds — one `sweep-holds` run off `oxsum.jobs`, whose chain the jobs worker keeps — the pass settles the rows older than `OXSUM_HOLD_TIMEOUT` at 0 with kind `swept`: the whole freeze is released and the settlement record marks the anomaly. The sweep writes the same usage row — zero counts and zero charge, with the attribution the watch row kept, so the row says whose turn timed out. A hold younger than the timeout is never touched — "old but still streaming" is excluded by the timeout contract, which must exceed the longest possible single request.
3. The sweeper and a late settlement share the derived settlement key, so both cannot take effect: whichever appends first wins, the other sees `Conflict("hold already settled")`, and the row is cleared either way.
4. A settle that keeps failing is counted on the row (`sweep_attempts`, `last_error`, `last_attempt_at`): at ten failures the row is dead-lettered — `dead_at` is set, the minute cadence drops to an hourly retry, and the hold surfaces to the operator three ways: the `holds_dead_lettered` reconciliation class, `deadAt` on `GET /api/v1/admin/holds`, and the `oxsum_holds_dead_lettered_total` / `oxsum_dead_holds` series. Dead is a reporting state, not a discard: the freeze stays stranded until a pass finally settles, which is why the hourly retry keeps running. See docs/decisions.md.

### User bill verification

1. Every booking returns a `contentHash` in the receipt; users keep it.
2. To verify, `GET entries/{id}/proof` returns the entry source, inclusion proof and tree head.
3. The client recomputes the hash from the source, checks it against the saved `contentHash`, then links the hash to the tree head with the proof. A single flipped byte in the source fails verification.
4. Why the user should trust the tree head itself: the operator signs each head (`GET /api/v1/log/head`), `GET /api/v1/log/key` publishes the verifying key, and `GET /api/v1/log/consistency?from=` proves that the current head extends one the user archived. The bills page runs that check for the user automatically: it archives the signed head in the browser's `localStorage` keyed by the log's origin, verifies the signature on every visit, and on growth fetches the consistency proof and verifies it in the browser through `oxsum_verify` (`web/` — the React bills page, issue #92; the check moved off the retired Topcoat crate with issue #256). Third-party witness cosignatures close the remaining trust in the operator's own key (issues #231, #259): `OXSUM_WITNESS_URLS` publishes each head to external `tlog-witness` endpoints whose cosigned notes are stored and served on `GET /api/v1/log/checkpoint`, and `OXSUM_WITNESS_KEYS` pins which `cosignature/v1` key each witness's line must verify against — served as `witnessKeys` so `oxsum_verify::verify_witnesses` can check them (see docs/decisions.md and the "Anchored heads" section of docs/user-guide.md). A deployment can also *be* one of those witnesses (issue #260): `OXSUM_WITNESS_SIGNING_KEY` + `OXSUM_WITNESS_TRUST` mount `POST /add-checkpoint`, which cosigns a foreign log's head only when it provably extends the head this witness last vouched for — the served head in `oxsum.witness_served`, every returned note filed append-only in `oxsum.witness_vouched`.
5. The price side of a settlement closes the same way (issue #204): a settlement description names `(channel, model, priceVersion)`, and the bundle carries a `price` link — the canonical row bytes plus a checkpoint the operator signed under `oxsum/price-catalog/<channel>`, `size` = the version, `root` = the tagged-BLAKE3 row hash (`oxsum/price-catalog/v1`), under the same `OXSUM_HEAD_SIGNING_KEY`. Signing is stateless and deterministic over (key, origin, version, row), so `receipt_proof` re-renders the identical note whenever it runs — a v1 bundle still verifies after v2 lands, and `GET /api/v1/log/price-head` serves the same checkpoint on demand; there is no snapshot table to drift. The verifier hashes the bundle's `row` string verbatim — the same pinned-wire rule `verify_charge` applies to descriptions — so the server never gets a second chance to spell the price.
   The *customer* terms of a sale-priced settlement close the same way on their own plane (issue #600): the v14 description may commit a `sale` digest — the resolved `SalePriceSnapshot`'s tagged-BLAKE3 hash under `oxsum/sale-catalog/v1` — and the bundle then carries a `sale` link beside `price`, the canonical snapshot row plus a checkpoint signed under `oxsum/sale-catalog/<businessId>` (`size` = the book version, `root` = the digest). The canonical row binds only the customer-visible identity — organization, model, book/draft/legacy provenance, effective window, and the `SalePrice` (which cannot carry `upstream` costs) plus `discountPercent` — so the evidence can never attest a supplier rate. `oxsum.sale_snapshot_digests` stores the canonical row once, keyed by its content-derived digest, so `receipt_proof` serves the identical bytes the settlement committed and `GET /api/v1/log/sale-head` re-signs the same note on demand. `verify_sale_head` reports `NotSalePriced` on a record committing no digest — a wholesale checkpoint must never be read as proving customer terms — and the gateway resolves and commits the digest at admission: `resolve_sale_price` runs once per request beside the route pick, a resolved snapshot replaces the organization's discount and reprices the freeze on the `SalePrice`, and a sale-priced turn keeps to the requested model (no cross-model fallback — issue #603, D04/D05).
6. A finalized statement closes the loop on the *rollups* too (issue #221): finalizing appends an anchor marker to the organization's ledger whose document hash is the window digest — `oxsum/statement-window/v1` folded over the covered entries' `contentHash` bytes in log order — and whose description carries the rollup digest (`oxsum/statement-rollup/v1` over the canonical `StatementRollupV1` bytes), while the statement row records `anchor_entry_id`/`anchor_log_index` plus the two digests (`windowHash`, `rollupHash`). The detail endpoints (org and admin) serve the anchor object, and `oxsum_verify::verify_statement_anchor` re-runs the client-side check — window fold equality, canonical-rollup digest equality, and on a signing deployment the note attesting the head at exactly `logIndex + 1` — so a verified bill also proves no covered entry was dropped, inserted, reordered or repainted.
7. The whole verification chain runs in the browser (WASM after hydration); the server only hands out raw bundles and never takes part in the verdict.

## Core entities

Only relationships; the ledger's table structure is authoritative in `crates/doubleentry/schema/postgres.sql`, oxsum's own in `crates/core/migrations/`.

- Organization 1-to-1 ledger, 1 ledger = 1 schema `ledger_<tenant_id>`, and an organization's tenant id is its own UUID without dashes.
- User many-to-many organizations, via memberships carrying a role (owner, admin, member). Registration creates one of each.
- Organization 1-to-many API keys; a key holds no balance itself, it is a credential resolving to its organization.
- Organization 1-to-many invitations (issue #59): a token link that registers a user straight into the inviting organization's memberships.
- User 1-to-many sessions (web login): built; a session acts as the organization the session row names, switched through `POST /api/v1/session/organization` or the dashboard's org switcher (issue #58).
- Every ledger's fixed accounts — the original nine plus the five the plan-fee journals added (issue #611):
  - `Liabilities:Wallet`: purchased balance, overdraft forbidden
  - `Equity:Bonus`: granted credit — the signup bonus and admin grants; settlement draws it after promo
  - `Equity:Promo`: promotional credit in live lots (issue #609) — the balance that can expire, so a hold draws it before everything else
  - `Equity:PromoExpiry`: the sink expired or cancelled promo burns to — a net-zero move out of the spendable pool, never a route back to refundable money
  - `Liabilities:CreditLine`: the drawn-down half of an organization's credit limit (issue #122) — its balance is undrawn credit; a hold or charge debits it exactly as it debits the wallet
  - `Assets:CreditFacility`: the commitment memo paired with the credit line — its debit balance is the granted limit, so what the organization owes is `limit − line balance`
  - `Assets:Cash`: money received from top-ups and plan-fee payments
  - `Income:Usage`: revenue recognized on settlement
  - `Equity:Adjustments`: operator-side money that is neither cash nor usage revenue — admin adjustments and the signup bonus draw on it, so grants and deductions stay out of the income line
  - `Assets:Receivables`: the open plan-fee balance a posted journal carries — what the customer still owes after the close's accrual
  - `Income:PlanFees`: the sold version's period fees, recognized at close — separate from usage revenue so a bill never blurs the two
  - `Income:Discounts`: the contra-revenue a credit-note correction or grant write-off carries
  - `Liabilities:UnearnedPlanFees`: the original `planPeriod` prepay: v1 close reclassifies it into receivable; v2 completed service days release it into revenue
  - `Liabilities:RefundPayable`: what a voided settled journal owes the customer back — the unwind destination when the receivable was already clear
- The pools a hold can draw are Promo, Bonus, Wallet and CreditLine, each carrying the `FundedReservations` limit, in promo → bonus → wallet → credit order — most-restricted money first. A hold reserves against what each pool carries — a pending debit on each pool it draws, so no pool's reservation exceeds what it holds — and a settlement releases exactly that split and charges in the same order. A deduction draws Bonus first as well. Granting or resizing the credit limit books the delta `debit CreditFacility, credit CreditLine` under a per-tenant advisory lock, and the line's own funding rule refuses a shrink below what is already drawn; a top-up credits the drawn part of the line first and the remainder to the wallet, so paying in repays debt before it adds own funds. What callers see stays one balance: every balance read sums the pools (undrawn credit included in `available`), while `creditLimitMinor`/`creditUsedMinor` report the facility separately. Ledgers written before the split migrate lazily, on their next `Wallet::open`: `reclassify_grants` moves the unspent remainder of historical grants — `clamp(grants - settled wallet outflow, 0, wallet balance)` — with one `debit Wallet, credit Bonus` entry under a fixed idempotency key, which spend reads exclude as a rebalancing rather than a charge.
- `oxsum.promo_lots` (migration 0092, issue #609) projects the promo pool into per-grant lots — `source` (`admin`/`grant`/`bundle_promo`/`legacy_migration`) and `source_ref` as the idempotency anchor, `remaining_minor` the unreserved fundable part, `expires_at` NULL for never — and `oxsum.promo_draws` pins which lots each hold's promo share took. The `expire-lots` job closes due lots once a minute, burning the unreserved remainder to `Equity:PromoExpiry`; a cancellation does the same for a refund, so promo can never convert back to cash. The bonus pool's aggregate balance migrated lazily into a never-expiring `legacy_migration` lot on the first open under this model, net balances unchanged. Every transaction that writes either projection takes the ledger's append advisory lock before its first promo row lock (issue #723): a hold pins its lots under that lock, so expiry, cancellation, settlement, granting and the legacy migration must acquire it first too — otherwise one side holds the append lock while waiting for a lot row the other locked while waiting for the append lock.
- One entry has many postings. Each posting sits in the settled or the pending layer, and the entry must balance within each layer.
- The Merkle log's leaves are the entries' content hashes.

## Authorized manual receipts (#624)

`manual_receipts.rs` stores immutable customer/key/reference/amount/reason and the operator authorization audit in one transaction before money moves. A distinct authority type is supplied by the authenticated deployment handler. Stable receipt UUIDs derive ledger keys, so an interrupted append/deposit/statement reconciliation can be recovered by the identical request. This bounded recovery path precedes T11/T15 transaction and payment-order work; there is no automatic recovery scan yet. Customer topups always refuse. Shared HTTP funding fixtures live only in `tests/support`, outside production routers; financial authority tests use the production router directly.

## Business ownership without ledger migration (#593)

Migration 0072 adds one deployment Business and maps every existing organization to a CustomerProfile keyed by the original organization ID. The profile holds business/external identity and lifecycle fields; existing membership, API keys, tenant pointers, wallet schemas, statements and proof origins are unchanged. An organization insert trigger assigns the same business in the creating transaction, covering signup, invitations, teams and seed without changing those identity paths. Empty accounts still create no ledger schema.

Channels and subscription plans acquire the business foreign key, with aliases/credentials/price history inheriting channel ownership and subscription periods inheriting plan ownership. Existing collection history stays with its customer. Environment-based merchant configuration remains the default-business bootstrap until T14. Singleton business storage refuses unsupported second-business creation.

An immutable business_migrations receipt captures counts at migration time. `ownership-preview` reads counts before migration without opening ledgers. Business staff is a separate, initially empty table: migration never promotes customer owners. Setup and staff capabilities are T03; configuration operations remain under deployment authority until that surface integrates.

## Initial owner transaction (#629)

`business_setup.rs` serializes setup on the singleton business row. Setup-token hashes live in `business_setup_tokens` with intended email, expiry, mint idempotency and acceptance. Existing-owner consent locks the live session/user/membership rows; fresh-owner registration uses `users::insert_registration` in the same transaction as staff assignment, profile initialization, token consumption and audit. No ledger is opened. The setup audit is immutable; customer identity mappings and old proofs are unchanged. Business session authorization and saved registration policy are enforced by `business_staff.rs`.

### Business authority and personal sessions (#630)

`business_staff.rs` resolves the live session secret and current staff role under the singleton business lock. Mutating business services must use `require_capability` in their own transaction before applying resource writes; the public read-only `business_capability` probe is not a reusable mutation grant. Staff changes, ownership transfer, account deletion and password reset share business-first locking. This prevents a transfer/delete race from appointing a tombstoned user or removing the last owner. Logout locks the session row directly and serializes with the guard's session share lock. Password verification runs before taking the lock; the password hash is rechecked under it before creating a session or TOTP challenge. TOTP challenge/code consumption and session creation commit in one transaction. Reset invalidates pending challenges as well as live sessions.

Migration 0074 adds the session's selected context and immutable `business_mutations` receipts. Customer organization selection is nullable so identity can survive losing its last customer membership. `authenticate_session` remains the customer resolver, joining current membership and requiring customer context; WebSocket and bill export share it. Business resolution never reads a customer role. Personal account handlers resolve identity separately without granting either commercial authority.

Public password and OAuth registration hold a shared business-policy lock through account creation. Owner policy writes take the exclusive business lock. `Db::register` remains a trusted provisioning primitive used by tests/seed; public signup calls `register_customer`. Legacy HTTP tests explicitly provision an open policy in guarded scratch databases, with no production switch or hidden middleware bypass. Production-router authority tests initialize through the real setup flow.

under the append lock so no admission can spend it between those steps. Its expiry
is always the immutable paid instant plus the sold lifetime.

Bundle refund review waits for completed fulfillment, preventing a later grant
from recreating refunded promotion. A trusted refund success cancels the lot
before the refund terminal mark; retrying the cancellation is idempotent. Open
hold draws retain their existing reservation and their unused release burns into
the closed lot. Promotion never contributes to the refundable purchased amount.
The existing refund correlation/recovery fixes have their own PRs and must be
integrated and revalidated together before candidate acceptance.

### Plan payment authority (#776)

`plan_payments.rs` computes a personal customer's sold-period quote under the
Business/assignment locks. Migration 0103 pins its snapshot on `payment_orders`,
adds one live order per assignment/index, and rejects new legacy/forged writes.
The snapshot stores customer plan, sold version, period index and renewal
bounds, exact sold fee, collection revision/currency and fiat ceiling. Initial
bounds are null; the first paid activation starts the service clock. A renewal
can be bought only once its preceding UTC boundary is due.

Activation locks the real paid order, the organization's subscription advisory
lock, subscription row, then assignment row. This matches admission and
rollover order. Historical authorization replay first verifies the same owning
customer/assignment; new effects require complete matching terms. An outstanding
refund reservation prevents a fresh grant. The wallet opens once before ledger
writes; reopening it after a close has appended can wait on the same transaction's
uncommitted ledger locks through a second pooled connection.

Every period fee prepays its own period in full. The removed arrears-first path
could divert a renewal into older debt and leave its new entitlement underfunded.
Explicit debt allocation is a separate #777 workflow. Period close propagates
partial as well as full prepayment to the customer statement, with an order-linked
allocation line. New sold-version renewal updates the quota engine's mirror,
quota and overage policy together. Historical ledger entries and completed
periods are not rewritten; daily versioned recognition remains N11/#737.

### Plan refund cash allocations (#802)

`plan_refunds.rs` owns the refund source and migration 0110's immutable
`plan_refund_effects`. The verified event path in `refunds.rs` holds the refund
lock, then follows activation's subscription advisory/row and plan-row order.
It locks the original journal before ledger/document writes. The ledger entry,
note application, bill/payment adjustments and allocation commit together.
An interrupted callback repeats the same refund identity. No original cash
allocation is selected from a different order or from the tenant's aggregate
unearned balance.

The allocation records full returned cash split between deferred prepayment,
earned-fee contra, refund payable, and explicit unallocated review suspense.
Closing a V1 period reads pre-close deferred allocations as source-linked
credits and applies only its original payment less returned cash. Statements
append a `refundCredit` and an opposing `paymentApplied` reversal after close:
charge total and applied payment fall together, preserving outstanding debt.
Zero-total refunded periods close paid. Voided journals retain their documents;
subsequent refunds draw their original refund payable.

Historical recovery reads the retained note's actual ledger postings, then
appends only the difference from the required allocation. Both old and new
entry identities stay in the effect. A correct historical cash entry requires
only the missing document/effect projection. A succeeded refund with an issued
note is recoverable before close; close refuses unresolved legacy sources.
Multiple ambiguous legacy allocations or combined legacy-refund/void histories
require explicit finance review. No migration rewrites ledger entries or
customer documents. See [the recovery runbook](plan-refund-recovery.md).

Refund and lost-dispute writers share the subscription/plan lock and preserve
both external cash facts in either order. Chargebacks read their original entry
on replay even after the journal becomes posted. Debt restoration is bounded by
the remaining applied payment; voided bills draw their source refund payable.
Any excess has an explicit suspense debit and review amount in the dispute
resolution audit. No cash result is clipped to a journal's remaining payment.

### Historical duplicate usage corrections (#809)

`plan_usage_corrections` inspects one exact old journal under business,
subscription, plan, journal, ledger-append and original-statement locks. It
verifies the original accrual, period's actual `Income:Usage` settlements,
source-specific prepayment and old Cash/Receivables payment entries, and the
matching statement. A typed report preserves source identities, content hashes
and allocation. Missing or combined correction history returns an explicit
refusal; apply audits that refusal without posting money.

Migration 0111 stores one immutable correction per journal. Successful apply
appends Dr PlanFees / Cr original open Receivables and/or RefundPayable, then
negative usage lines and any payment-to-payable reversal on the original
documents. Cash never moves. The effect, entries, counters and audit commit
atomically; all original entries and writer guards remain. Cleared debt may
lift only the already-locked plan's dunning flag. The local command defaults to
dry-run and uses `Wallet::open_existing`; it does not bootstrap a ledger or call
a PSP. See [the runbook](plan-usage-correction.md).

The correction's immutable funding map includes the authorizing order and every
allocated historical cash order. Refund requests and approvals serialize with
correction on the business row and refuse these sources before provider I/O.
Later confirmed cash outcomes use the source map before ordinary period
allocation: the full cash outflow is retained as review suspense, naming the
corrected journals, without consuming another period's deferred balance or
automatically clearing the correction payable. The standing cash entry provides
chargeback replay; refund effects retain their own idempotent allocation.

### Daily recognition sources (#838)

`plan_accounting_periods` freezes each v2 authorization, version, fee and exact service bounds beside its activation invoice. `plan_accounting_effects` records activation, one effect per completed UTC date, refunds, disputes and voids with exact ledger entry IDs. Every effect conserves `billed = earned + deferred` and `receivable = billed - collected`. Inputs/effects are append-only; current net values are sums. The durable `plan-recognition` worker advances through eligible periods, owns the plan row, locks the journal and then ledger append, and commits the daily row beside the official entry. Refund/void use the same catch-up and lock order. Old service dates are metadata; late work posts to today's open ledger date.

V2 invoices issue before earning: prepaid activation creates a paid journal/statement without Receivables/PlanFees accrual. The period close finds the immutable accounting row even if its invoice is void and cannot reissue. A refund first catches up completed days, recomputes net earned under reduced consideration and debits earned contra plus remaining original deferred. A dispute changes collection/receivable (or payable after void), never the service interval or earned amount. The same source-linked effect records feed reports and exported evidence.


Evidence minting freezes exact artifact inputs durably in `evidence_mint_inputs`
before appending its deterministic scope marker. An atomic unique scope insert selects
the winning snapshot; concurrent mints reload it and return the persisted descriptor.
No database connection is retained across nested ledger calls.
If a process fails after marker append but before exported bytes persist, retry
uses those frozen inputs even when later refunds or daily recognition have landed.
An older orphan marker with no matching captured inputs explicitly refuses
publication rather than serving an export bound to a different digest. Existing
stored bundles remain unchanged; independent ledger verification still requires
the retained trust inputs and stays within the documented proof scope.


Runtime independent ledger reconciliation remains [#848](https://github.com/AllureCurtain/oxsum/issues/848):
the existing `actualTotals` snapshot still clones the projection. Daily accounting
fixtures independently compare postings, but that development evidence does not
turn the current runtime report into an independent ledger audit.

### Stable application-owned accounts (#846)

Migration 0114 adds immutable `integration_applications`, `application_customers`
and `integration_customer_operations`. The application-to-customer mapping owns
no money: it names the existing organization and its ledger, retaining the business
profile's independent immutable external ID. An application selects a lifetime
customer bound, and archival never releases capacity or identity for reuse.

An integration credential optionally points to exactly one application. Every
scope check reloads revocation, expiry, scope and namespace before checking the
customer mapping. Explicit legacy grants remain separate. Business mutations take
the business lock before credential and admission locks; provision, mapping,
receipt and service audit commit together. Original request/result snapshots are
immutable and use an application keyspace across credential rotation. Old
provisioning receipts can be adopted only after checking the original service
actor, exact terms and customer identity; ambiguity refuses for source review.

Application metering retains its existing authorization/hold/settlement machinery.
Its stable operation fingerprint uses application plus customer plus request key;
original credential provenance is pinned in admission metadata. Completion checks
that the current credential belongs to the same application and holds the needed
scope. Legacy credentials keep their previous fingerprints and authority.

### Transaction-bound ledger source reads (#856)

`ledger_source` reconstructs complete `StoredEntry<SCALE>` values on a borrowed
`PgConnection` and calls the public engine's canonical hash verification. Raw
idempotency bytes, booking/value dates, description, kind, provenance, document
references, reversal metadata, posting order, account IDs, currencies, layers and
dimensions are preserved. Missing sources stay missing; malformed or corrupt
entries retain per-entry failures in batch reads; operational database errors
abort the read. A content hash does not prove log inclusion, entry-ID-to-key
mapping, account-path labels, or original business ownership. Consumers must
compare the verified raw key and registered account IDs with their exact source;
financial reconciliation must also require an official log index.

Wallet transaction paths read their calendar, sealed-day state, source entries,
receipts and outstanding holds on the same connection as their append. Credit
repayment and credit-limit changes keep the append inside the transaction that
holds their credit lock. A transaction sees its own newly appended entry and
cannot starve the pool by checking out a second slot. The caller chooses the
isolation level: independent reconciliation needs a repeatable-read snapshot;
ordinary mutations retain their existing locking and isolation policy. The
helper neither opens a transaction nor changes the caller's isolation level.
No ledger-engine schema or canonical encoding changes are required.

### Non-plan refund cash and historical recovery (#841)

`nonplan_refunds/{evidence,apply,recovery,types}.rs` owns exact receipt/source
verification, transaction-owned Cash and the explicit local recovery boundary.
Migration 0115 keeps immutable effects separate from the original approval/note
state. Business and organization parent key-share locks precede the shared
non-plan order-source, refund and append locks;
actual Cash, source promotion cancellation, note projection, effect and applicable
human finance audit commit together. External unapproved cash uses null-note
source evidence and review suspense, never a fabricated staff actor.

Original funding and intervening activity use the engine's canonical content-hash
verification on the borrowed transaction connection (#856). The bounded source
inspection verifies at most 20,000 sequenced entries; a larger history retains
fresh Cash in review suspense and refuses historical Wallet restitution.
The conservative bound excludes later credits, subtracts settled debits and
outstanding pending reservations, and counts previous actual returns once. New
atomic refund rows can prove no effect; old rows retain an uncertain-source fence.
Historical restitution uses an exclusive original return `log_index`, not today's
Wallet balance. The source revision includes ledger boundary, Wallet activity
hash and prior return identities/hashes. Existing Cash and note pointers remain;
only a missing Cash leg or a proven Wallet restitution is appended.

`cashEffect` is an additive customer/finance projection. Actual late cash counts
against refundable bounds and excludes payout retries even if terminal state
cannot change. An unfulfilled returned purchase stays in reconciliation and
cannot receive a future grant. The recovery CLI uses explicit database/session
inputs without dotenv, migrations, lazy wallet creation or provider I/O.
