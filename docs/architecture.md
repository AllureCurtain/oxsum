# Architecture

## Overview

```
Browser ──→ React dashboard /app (Vite build, rust-embed'd)         │
          ──→ /verify, server-rendered skeleton + wasm verifier (Topcoat) │
LLM clients ──→ Gateway /v1/chat/completions, /v1/messages, ───────┤  one process, one binary
                /v1/embeddings, /v1/rerank                          │
API callers ──→ axum /api/v1 ──────────────────────────────────────┤
                                                                   ▼
                     oxsum-core (Wallet / Tenants / Db)  ──→ upstream LLM (gateway relay)
                                                                   ▼
                     doubleentry (bookkeeping, Merkle log)
                                                                   ▼
                     PostgreSQL: one ledger schema per organization, plus one `oxsum` schema
                     holding users, organizations, memberships and API keys
```

The axum API, the core, doubleentry and the gateway exist today, with oxsum's own identity tables in one `oxsum` schema. The user-facing dashboard is the React app under `web/` — built once, embedded into the binary and served at `/app` (issue #234); it reached parity and the server-rendered Topcoat pages retired to it (issue #256), so the legacy page paths now `301` to their `/app` twins and only the public `/verify` check stays server-rendered.

| Tree heads | `crates/core/src/heads.rs`, `Wallet::{signed_head, consistency}` | The operator's signed tree heads: the per-tenant origin (`oxsum/ledgers/<tenant_id>`), the C2SP signed-note signed under `oxsum/tree-heads`, and the key publication. | HTTP | `crates/server/src/` | Routing, API-key middleware, error mapping, and the dashboard's own routes outside `/api/v1` (the billing WebSocket and the bills export) |
| Gateway | `crates/server/src/gateway/` | The `/v1` surface: model list, `chat/completions` in OpenAI's shapes, `messages` in Anthropic's, and the input-only `embeddings`/`rerank` surfaces in OpenAI's — each surface serves only the channels that declare its protocol *and* price the model under the surface's billing mode, and errors come back in the shape that surface's SDK parses. The relay that freezes before upstream and settles however the turn ends is shared by all four. Its own auth middleware, because a refusal here has to look like the client's own protocol's. It resolves the model's routes from the rows in `crates/core` once per request — one per channel, each a `(channel, version, weight, price)` — orders them with a weighted pick followed by descending weight (`route_order`), and freezes the dearest candidate's bound so whichever route answers stays inside the hold. A refusal before the first answer byte (unreachable, 429, 5xx) rotates to the next route; a last route's 429 naming a short `Retry-After` is waited out once; a refusal after bytes flow is never retried. The settlement records the answering channel and version plus `upstreamAttempts` (description v5), and the surface's `(protocol, endpoint)` pair resolves into the `UsageAdapter` that reads its usage reports — `embeddings` reads `usage.prompt_tokens`, `rerank` reads `usage.total_tokens`. Pricing is in core, see docs/decisions.md. It notes each hold in the sweeper's watch table before taking it, and clears the row when the turn settles |
| Hold sweeper | `crates/core/src/holds.rs`, run by the jobs worker | The `sweep-holds` periodic job: settles watched holds older than `OXSUM_HOLD_TIMEOUT` at 0 with kind `swept`, releasing the whole freeze. The watch table (`oxsum.open_holds`) is a finding aid only: the ledger stays the source of truth, and the derived settlement key is the atomic guard against a late settlement landing alongside the sweep. See docs/decisions.md |
| Jobs worker | `crates/core/src/jobs.rs` (the table), `crates/server/src/jobs.rs` (the loop) | The durable periodic-work layer (issue #166): one `oxsum.jobs` row per scheduled run, claimed `FOR UPDATE SKIP LOCKED` under a 300-second lease — multi-instance safe, crash-resumable. Leader-required kinds (`sweep-holds`, `witness-checkpoints`, `statements`, `retention`, `sync-upstream-prices`, `usage-anchors`, `reconcile`) additionally run under a session-scoped advisory lock held on a dedicated connection for the whole pass (issue #281): a worker claiming a leader-required row whose lock is held hands the row back to `pending` — so a pass that outlives its claim lease is never duplicated mid-flight, and a crashed holder's lock frees with its connection. Kinds: `sweep-holds`, `deliver-webhooks` (unleadered: its rows are claimed individually, a second runner is throughput), `sync-upstream-prices` (daily; scheduled only when `OXSUM_UPSTREAM_PRICE_SYNC` is set *and* `OXSUM_SECRET_KEY` exists to unseal channel credentials — issue #222), `reconcile`, `statements` (the ended month's `close_month` + draft generation + overdue flip + the dunning sweep — issue #258), `usage-anchors` (daily; commits yesterday's sorted-map root over every customer's day-log head into each organization's ledger — issue #338), `retention` (the batched `OXSUM_RETENTION_*` cleanup). A run failing five attempts lands `dead` — the `jobs_dead` reconciliation class's evidence — while the kind re-enqueues an hour out |
| Admin | `crates/server/src/admin.rs` | The platform admin's `/api/v1/admin` surface: channels and their price versions, organizations and adjustments, anomalies and the margin view, redemption-code minting — behind `OXSUM_ADMIN_TOKEN` in a middleware of its own, because this is not an organization's credential. The anomalies list scores each row 0–100 at read time (`crates/core/src/anomaly.rs`): the kind's base weighted by the charge ratio, upstream-cost shortfall, failover attempts and the request id's repeat count from `usage_records` — read-only, never an input to the charge. Store and rules are in core, see docs/decisions.md |
| Deposits | `crates/core/src/deposits.rs`, `crates/integrations/src/stripe.rs` | The single record of money arriving: one `oxsum.deposits` row per rail payment, keyed `(rail, organization_id, payment_ref)`, status-walking `pending → confirmed → credited \| reversed \| expired` with `entry_id` naming the ledger entry once credited. Rails today: `manual` (every `/topups`), `redemption` (`oxsum.redemption_codes` — SHA-256-only codes, `FOR UPDATE` claim, ledger credit under `redemption:<code_id>`, crash-resumable) and `stripe` (issue #201 — the caller's `idempotencyKey` stays the `payment_ref`, the Checkout session id and hosted URL live in `meta`, and the signed webhook confirms then credits under `stripe:<session_id>`; `stripe.rs` is the narrow client — form-encoded session POST, `Stripe-Signature` HMAC verify — env-gated by the `OXSUM_STRIPE_*` trio all-or-none at boot). The `x402` rail (issues #264, #282) credits a signed payment authorization in one request — `RailVerifier` is the seam with verify and settle legs: the real rail delegates both to an x402-rs facilitator sidecar (`OXSUM_X402_FACILITATOR_*`, all-or-none) that verifies on-chain and settles under the deposit row's `FOR UPDATE` so a `payment_ref` nonce settles at most once (`facilitator_tx_hash` on the row); the `Ed25519RailVerifier` stand-in checks the canonical-body signature against `OXSUM_X402_VERIFYING_KEY` and settles trivially — `payment_ref` is the signed `nonce`, and the credit replays under `x402:<nonce>` |
| Display currency | `crates/core/src/display.rs`, `Config::display_for` | The fiat rendering of a credit amount (issue #257): `DisplayCurrency` — ISO code, a decimal-text `rate_per_credit` and a decimals count — stored as a pair of `text` columns on `oxsum.organizations` (migration 0043). `Display::render` converts a minor-unit amount by pure i128 mantissa/scale arithmetic (half-up at the chosen decimals) — never a float — so the same amount renders identically in the statement PDF, the bills exports and the React dashboard. Resolution order is the organization's stored pair, then the `OXSUM_DISPLAY_*` default, then nothing |
| Statements | `crates/core/src/statements.rs`, `crates/core/src/statement_pdf.rs`, `crates/core/src/heads.rs` | The monthly billing documents: `oxsum.statements` (one per organization and UTC `YYYY-MM`, `draft → finalized`, payment standing `pending | paid | overdue | suspended`, terms and due date snapshotted at issue, `log_from_index`/`log_to_index` pinning the ledger window the lines prove) and `oxsum.statement_lines` (the period's usage aggregated by channel and model). | Usage reports | `crates/core/src/usage_reports.rs`, `crates/core/src/heads.rs`, `Wallet::{anchor_usage_report, usage_report_bundle}` | The end-user signed reports (issue #261): an organization bills its downstream customers out of a ledger that mixes every customer's usage, so a customer cannot verify a bill by reading the log. `POST /api/v1/org/usage-reports` mints `{endUser, from, to}` — `usage_report_subset` selects the `status='settled'` `usage_records` attributed to the `endUser` whose settlement entries book inside the (fully ended) span, folds their content hashes under `oxsum/usage-report/v1`, and `anchor_usage_report` appends a self-balancing 1-minor `Equity:Adjustments` marker whose `DocumentRef` binds that digest and whose description commits the canonical `UsageReportV1` `{endUser, from, to, entryCount, chargedTotalMinor, subsetHash}`. `oxsum.usage_reports` + `oxsum.usage_report_rows` (migration 0045) freeze the descriptor and the committed subset — a re-fetch serves the frozen rows, never a re-query — and the marker's `usage-report/<endUser>/<from>/<to>` idempotency key plus the `(tenant_id, end_user, from_date, to_date)` UNIQUE make one report per span ever. `usage_report_bundle` assembles the marker and every shown entry's inclusion proof under one head (each proven at that head's size) so a bundle is self-consistent while the ledger grows; `oxsum_verify::verify_usage_report` runs the offline check. Share links (issue #300) live in `oxsum.report_links` (migration 0052): `scope` is `report` (one minted report) or `end_user` (one customer's issued reports), `token_hash` is the only form stored, and `resolve_report_link` touches `last_used_at` and answers expired, revoked and unknown tokens as the same `None` — the bill page turns that into one 404 |

| Request idempotency | `crates/core/src/idempotency.rs` | The `Idempotency-Key` claims table (`oxsum.idempotency_records`, migration 0016): one row per `(organization, key)` carrying the request fingerprint, the minted request id and the stored answer. | Reconciliation | `crates/core/src/reconcile.rs` | The drift scan behind `GET /api/v1/admin/reconciliation` and the `/admin/reconciliation` page: every organization's ledger read against the oxsum-owned projections — usage rows, deposits, hold watches — one report entry per drift class with a count and a bounded sample. | Upstream price sync | `crates/core/src/upstream_sync.rs`, driven by `crates/server/src/jobs.rs` | The stored-versus-live side of upstream cost (issue #222): the daily `sync-upstream-prices` job probes each channel's `GET {baseUrl}/api/v1/pricing` — the channel must be another oxsum deployment — with the unsealed credential, and diffs every model's live `upstream` block against the stored `upstream_prices`. `oxsum.upstream_price_drift` is open state, not an event log: one row per divergent `(channel, model, field)`, upserted on re-detection, `resolved_at` set the moment the rates agree again — and each open broadcasts `anomaly.detected` at platform scope via `broadcast_event`. `oxsum.upstream_price_probes` records every probe's outcome (`ok`, `unreachable`, `invalid`, `auth`), so a failing channel leaves evidence instead of silence and never fails the pass. The CSV and JSON export beside the bills list stays a server route (`/dashboard/bills/export.*`), because a download has to be a response (docs/decisions.md) |
| Mandates | `crates/core/src/mandates.rs` | Signed spend mandates (issue #262): a key holder delegates a strictly narrower slice of a key's authority to a bearer who does not hold the key. `oxsum.mandates` (migration 0041) is the metadata row — cap, model subset, `not_before`/`not_after` — and `api_keys.mandate_signing_seed` holds the Ed25519 seed the key's mandates sign under, sealed like a channel credential. `POST /api/v1/org/keys/{keyId}/mandates` mints the signed blob; the delegate presents it in `X-Oxsum-Mandate` on `/v1/*` and `/api/v1/holds`. Admission verifies the signature against the key's public half, then `hold_for_key` enforces window, model subset and cap under the per-key advisory lock — the committed figure summed from the ledger's own postings by the mandate id each entry writes as its provenance correlation, the same derivation `key_committed_in` uses per key. A settled delegated turn's v7 settlement description names the mandate `{id, hash}` so `/verify` proves which delegation authorized it |

Principle: **domain logic belongs in core; the gateway does protocol and orchestration only; server only assembles**. The litmus test — if the logic survives replacing the axum layer, it is in the right place. That is why the gateway is a module of the server crate rather than a crate of its own: everything it does is HTTP — routing, an OpenAI-shaped error body, request deserialization, and a relay whose lifetime is the response body's — while every number it charges by is computed in `crates/core/src/billing.rs` and every row it charges by is read through `crates/core/src/channels.rs`. Migrations follow the crate that owns the table (core's tables in `core/migrations/`), applied in dependency order at startup.

## Frontend/backend boundary

- External callers use REST/JSON; the contract is `crates/server/openapi.yaml`.
- The dashboard is a single-page React app (`web/`) served at `/app`; it talks to `/api/v1` in the browser, with no server-side page handlers. The bills export (`GET /dashboard/bills/export.csv` and `.json`) stays a server route — a download is a response, not a page — and the platform-admin pages call `/api/v1/admin/*` straight from the browser with the operator token, because that bearer credential is the deployment's and no session could hold it (docs/decisions.md).
- The one page still server-rendered is `/verify` (in `crates/web`): the skeleton is a plain form whose `verify.js` loader runs the `oxsum_verify` wasm build in the browser when the bundle ships (issue #284) — the verifier's bytes travel to the client rather than the client trusting a verdict the server rendered — and the form's native POST runs the same `oxsum_verify` on the server as the no-JavaScript floor. `crates/verify` is wasm32-clean by design (uuid's wasm32 randomness solved with the `js` feature, see docs/decisions.md); its `wasm` feature exports the `verify_*` functions over wasm-bindgen, and `scripts/build-verify-wasm.sh` produces the bundle `crates/web` embeds — a build without the toolchain ships the committed placeholder and the page stays on the server path.

## Auth and permissions

- API: an organization's API key in `Authorization: Bearer oxs-…`, or a session cookie from web login — both resolved to a principal (the organization, or the user plus their role in it) by middleware; handlers read the principal from the request, never from the path. Neither credential's plaintext is stored: the database keeps SHA-256 hashes and display prefixes.
- Web login: self-built session table (token hash, user id, organization id, expiry, revocation), cookie with HttpOnly, SameSite=Lax, Secure when the deployment says so; password hashing with password-auth (argon2). A session dies with its membership. Rationale in docs/decisions.md.
- Role rules: members list and revoke only the keys they created (anything else is 404), owners and admins see and revoke all; roles constrain sessions, not keys. One exception, and it is deliberate: managing memberships needs a session in the owner or admin role, so a key is refused there even though it acts as the whole organization — a key is not a person and names no role (docs/decisions.md, "membership management is a person's action"). The member list itself stays readable by every member.
- Between tenants: physical isolation, one schema per tenant, no filter columns in queries. The connection layer shares one pool; `SET LOCAL search_path` at the start of each transaction picks the tenant schema (mechanism in docs/decisions.md). oxsum's own tables are not in those schemas: they are schema-qualified (`oxsum.users`) in the one `oxsum` schema, so nothing about a request's organization can change which identity rows a statement sees.
- Planned:
  - Last-used timestamps on API keys, see TODO.md.
  - See docs/decisions.md and TODO.md.

## Core data flows

### Billing for one streaming call

1. Before relaying an LLM request, `POST holds` freezes an upper bound.
   - The pool accounts book a debit in the pending layer, split bonus → wallet → credit — `Equity:Bonus` funds what it can, `Liabilities:Wallet` carries what it can, and `Liabilities:CreditLine` carries the rest while undrawn credit remains; available balance drops accordingly.
   - All three pools carry a `FundedReservations` limit; the limit check and the write happen in one database transaction, with the pending layer included in the calculation, so concurrent holds cannot overdraw the pools or the credit line. A hold whose split a racing append invalidated retries with balances re-read rather than refusing a request the combined balance could have served.
   - A gateway request does this itself, before it opens the upstream connection: the freeze is computed in `crates/core/src/billing.rs` from the request text and the output ceiling, and its refusal is answered as OpenAI's 402.
   - Before the freeze, admission enforces the organization's tier (issue #158): the profile's model allowlist refuses a model it does not name (403), and its `requests_per_minute` spends one rolling-minute window keyed on the organization — shared by every key it owns — beside the key's own allowance below. The tier is never a pricing input.
   - Beside the price version, the turn also resolves its discount once at start (`Db::discount_percent`): the single most favorable `pricing_discounts` row matching the organization, the model and the moment. The snapshot rides the turn into the settlement, where it scales the summed numerator down by `percent` — one ceiling division — before the freeze's `min` applies.
   - Suspension gates the same point (issue #162): `organizations.suspended_at` is read inside `hold_for_key` and `hold` — every admission path shares them — under an org-scoped advisory lock the hold takes shared and `Db::set_suspended` takes exclusive, so a hold either observes the flag or committed before it. A suspended organization's in-flight holds still settle and money-in still lands: the flag writes nothing into the ledger. Suspending enqueues `org.suspended` for the organization's subscribed webhook endpoints in the flag's own transaction; a replayed flag emits nothing. The `statements` job's dunning sweep sets the same flag itself (issue #258): an opted-in organization (`dunning_grace_days`) whose finalized statement stands unpaid past `due_date + grace` is suspended with `dunning_suspended_at` marking the sweep as the suspender, and a later pass lifts a sweep-set suspension once nothing unpaid stands past grace — or when the grace is switched off — while a suspension the operator set by hand (`dunning_suspended_at` NULL) is never the sweep's to undo.
   - Key constraints are enforced inside `Wallet::hold_for_key`, in the transaction that holds the per-key advisory lock and the locked key row (issue #120): the model allowlist is checked against the model the gateway names (`POST /api/v1/holds` passes none and is not governed), and the spend limit reads the constraint row in force — a `budget_duration` makes the committed read periodic, counting the current UTC window's settled charges plus every outstanding hold whatever its age. A replayed hold answers before either check, so a retry cannot be refused by a constraint that changed after its first landing.
   - A member's budget is checked in the same window (issue #162): `memberships.budget_limit_minor` — set on `PATCH /api/v1/org/members/{userId}` — caps the committed spend summed over every key `api_keys.created_by` attributes to the member. The membership row is locked for update inside the hold transaction, so two of the member's keys cannot both slip under the cap; the sum itself is the ledger's — settled charges plus outstanding holds, same provenance `key_committed_in` reads.
   - A presented mandate's bounds run in the same window too (issue #262), after the key's own: the entry writes the mandate id as its provenance correlation, so `mandate_committed_in` sums settled charges plus outstanding holds under that id — the same postings sum, sliced by the delegation instead of the key. A settle copies the hold entry's correlation onto the charge the way it copies the actor, so the mandate's committed total stays ledger-derived across the hold → settle handoff and a racing second delegated hold cannot both fit.
2. When the stream ends, `POST settlements` books one entry that does two things:
   - Books a reversal in the pending layer, releasing each pool's slice of the hold
   - Charges actual usage in the settled layer, bonus pool first, moving pools → revenue
   - The same limit checks the release as a backstop, so the amount it gives back cannot exceed what holds reserved. The pairing itself is one-to-one: a settlement names the hold it releases, and the hold's entry is the amount — see docs/decisions.md.
   - The gateway settles when the relayed stream ends, and the settlement is awaited before the stream closes, so a client that read a stream to its end reads a settled bill. The write runs in a task of its own, so a client that hangs up while it is being appended cannot cancel it; a client that hangs up before that cancels the upstream call and settles what had been forwarded from a local estimate.
   - Beside a settlement that landed, the same path writes the turn's normalized usage row to `oxsum.usage_records` (`crates/core/src/usage.rs`, issue #102): the full dimensions pricing looks at, the caller's attribution, and `usage_details.provider_raw` — the mutable-store data an immutable entry description cannot hold. The entry stays the source of truth; a failed row write is drift for the reconciler to report, not a reason to retry the charge.
   - The same write also rolls the turn into `oxsum.usage_daily` in the same transaction (issue #126): one row per `(tenant, booking day, key, channel, model)` sums turns, tokens and charge. The day key is the settlement entry's `booking_date` — the ledger's day, not the write's instant — so the rollup agrees with the statement period's seam. A replayed usage write inserts no row and rolls nothing; a usage row whose settlement entry is missing aggregates nothing and stays reconciler-visible drift.
   - The same write also refreshes the customer's **usage day log** (issue #337): one row per `(tenant, endUser, booking day)` holding the day's settlement count, the Merkle root over that day's settlement content hashes in log order, and the domain-tagged day leaf. The root is recomputed from the settled rows rather than appended incrementally, so it can never disagree with the rows it claims; a day with no settled usage has no row. A later stage anchors these leaves in the ledger and carries them in the report bundle, which is what turns "completeness is the organization's claim" into a proof (docs/decisions.md, 2026-10-22).
   - The same write also records `upstream_cost_minor` (issue #112): `Price::upstream_cost` resolves the same set the turn priced under and prices the usage at upstream's rates, so the row holds what the platform paid beside what it charged. The column is nullable by design — untracked, not zero, for a price without an `upstream` block, a swept turn, or history — and `Db::margin` sums the pair per `(channel, model)` for the admin margin view, counting the NULLs as `untrackedTurns`. Upstream cost never enters a settlement description or an organization-facing endpoint.
3. Each step carries its own `idempotencyKey`, so retries are safe. For a gateway turn the hold's key is derived from the request id the response header carries (`req-<id>:hold`), and the settlement's key is derived from the hold's (`oxsum_core::settlement_key_for`).

### The hold sweeper

1. The gateway notes each hold in `oxsum.open_holds` *before* taking it, and deletes the row when the turn settles — however the turn ends, including the `Drop` path for a client that disconnects mid-stream. A row without a hold (the process died in between) heals itself: the sweeper deletes it when the hold is not there.
2. Every 60 seconds — one `sweep-holds` run off `oxsum.jobs`, whose chain the jobs worker keeps — the pass settles the rows older than `OXSUM_HOLD_TIMEOUT` at 0 with kind `swept`: the whole freeze is released and the settlement record marks the anomaly. The sweep writes the same usage row — zero counts and zero charge, with the attribution the watch row kept, so the row says whose turn timed out. A hold younger than the timeout is never touched — "old but still streaming" is excluded by the timeout contract, which must exceed the longest possible single request.
3. The sweeper and a late settlement share the derived settlement key, so both cannot take effect: whichever appends first wins, the other sees `Conflict("hold already settled")`, and the row is cleared either way.
4. A settle that keeps failing is counted on the row (`sweep_attempts`, `last_error`, `last_attempt_at`): at ten failures the row is dead-lettered — `dead_at` is set, the minute cadence drops to an hourly retry, and the hold surfaces to the operator three ways: the `holds_dead_lettered` reconciliation class, `deadAt` on `GET /api/v1/admin/holds`, and the `oxsum_holds_dead_lettered_total` / `oxsum_dead_holds` series. Dead is a reporting state, not a discard: the freeze stays stranded until a pass finally settles, which is why the hourly retry keeps running. See docs/decisions.md.

### User bill verification

1. Every booking returns a `contentHash` in the receipt; users keep it.
2. To verify, `GET entries/{id}/proof` returns the entry source, inclusion proof and tree head.
3. The client recomputes the hash from the source, checks it against the saved `contentHash`, then links the hash to the tree head with the proof. A single flipped byte in the source fails verification.
4. Why the user should trust the tree head itself: the operator signs each head (`GET /api/v1/log/head`), `GET /api/v1/log/key` publishes the verifying key, and `GET /api/v1/log/consistency?from=` proves that the current head extends one the user archived. The bills page runs that check for the user automatically: it archives the signed head in the browser's `localStorage` keyed by the log's origin, verifies the signature on every visit, and on growth fetches the consistency proof and verifies it in the browser through `oxsum_verify` (`web/` — the React bills page, issue #92; the check moved off the retired Topcoat crate with issue #256). Third-party witness cosignatures close the remaining trust in the operator's own key (issues #231, #259): `OXSUM_WITNESS_URLS` publishes each head to external `tlog-witness` endpoints whose cosigned notes are stored and served on `GET /api/v1/log/checkpoint`, and `OXSUM_WITNESS_KEYS` pins which `cosignature/v1` key each witness's line must verify against — served as `witnessKeys` so `oxsum_verify::verify_witnesses` can check them (see docs/decisions.md and the "Anchored heads" section of docs/user-guide.md). A deployment can also *be* one of those witnesses (issue #260): `OXSUM_WITNESS_SIGNING_KEY` + `OXSUM_WITNESS_TRUST` mount `POST /add-checkpoint`, which cosigns a foreign log's head only when it provably extends the head this witness last vouched for — the served head in `oxsum.witness_served`, every returned note filed append-only in `oxsum.witness_vouched`.
5. The price side of a settlement closes the same way (issue #204): a settlement description names `(channel, model, priceVersion)`, and the bundle carries a `price` link — the canonical row bytes plus a checkpoint the operator signed under `oxsum/price-catalog/<channel>`, `size` = the version, `root` = the tagged-BLAKE3 row hash (`oxsum/price-catalog/v1`), under the same `OXSUM_HEAD_SIGNING_KEY`. Signing is stateless and deterministic over (key, origin, version, row), so `receipt_proof` re-renders the identical note whenever it runs — a v1 bundle still verifies after v2 lands, and `GET /api/v1/log/price-head` serves the same checkpoint on demand; there is no snapshot table to drift. The verifier hashes the bundle's `row` string verbatim — the same pinned-wire rule `verify_charge` applies to descriptions — so the server never gets a second chance to spell the price.
6. A finalized statement closes the loop on the *rollups* too (issue #221): finalizing appends an anchor marker to the organization's ledger whose document hash is the window digest — `oxsum/statement-window/v1` folded over the covered entries' `contentHash` bytes in log order — and whose description carries the rollup digest (`oxsum/statement-rollup/v1` over the canonical `StatementRollupV1` bytes), while the statement row records `anchor_entry_id`/`anchor_log_index` plus the two digests (`windowHash`, `rollupHash`). The detail endpoints (org and admin) serve the anchor object, and `oxsum_verify::verify_statement_anchor` re-runs the client-side check — window fold equality, canonical-rollup digest equality, and on a signing deployment the note attesting the head at exactly `logIndex + 1` — so a verified bill also proves no covered entry was dropped, inserted, reordered or repainted.
7. The whole verification chain runs in the browser (WASM after hydration); the server only hands out raw bundles and never takes part in the verdict.

## Core entities

Only relationships; the ledger's table structure is authoritative in `crates/doubleentry/schema/postgres.sql`, oxsum's own in `crates/core/migrations/`.

- Organization 1-to-1 ledger, 1 ledger = 1 schema `ledger_<tenant_id>`, and an organization's tenant id is its own UUID without dashes.
- User many-to-many organizations, via memberships carrying a role (owner, admin, member). Registration creates one of each.
- Organization 1-to-many API keys; a key holds no balance itself, it is a credential resolving to its organization.
- Organization 1-to-many invitations (issue #59): a token link that registers a user straight into the inviting organization's memberships.
- User 1-to-many sessions (web login): built; a session acts as the organization the session row names, switched through `POST /api/v1/session/organization` or the dashboard's org switcher (issue #58).
- Every ledger has seven fixed accounts:
  - `Liabilities:Wallet`: purchased balance, overdraft forbidden
  - `Equity:Bonus`: granted credit — the signup bonus and admin grants; settlement draws it before the wallet
  - `Liabilities:CreditLine`: the drawn-down half of an organization's credit limit (issue #122) — its balance is undrawn credit; a hold or charge debits it exactly as it debits the wallet
  - `Assets:CreditFacility`: the commitment memo paired with the credit line — its debit balance is the granted limit, so what the organization owes is `limit − line balance`
  - `Assets:Cash`: money received from top-ups
  - `Income:Usage`: revenue recognized on settlement
  - `Equity:Adjustments`: operator-side money that is neither cash nor usage revenue — admin adjustments and the signup bonus draw on it, so grants and deductions stay out of the income line
- The pools a hold can draw are Bonus, Wallet and CreditLine, each carrying the `FundedReservations` limit, in bonus → wallet → credit order. A hold reserves against what each pool carries — a pending debit on each pool it draws, so no pool's reservation exceeds what it holds — and a settlement releases exactly that split and charges in the same order. A deduction draws Bonus first as well. Granting or resizing the credit limit books the delta `debit CreditFacility, credit CreditLine` under a per-tenant advisory lock, and the line's own funding rule refuses a shrink below what is already drawn; a top-up credits the drawn part of the line first and the remainder to the wallet, so paying in repays debt before it adds own funds. What callers see stays one balance: every balance read sums the pools (undrawn credit included in `available`), while `creditLimitMinor`/`creditUsedMinor` report the facility separately. Ledgers written before the split migrate lazily, on their next `Wallet::open`: `reclassify_grants` moves the unspent remainder of historical grants — `clamp(grants - settled wallet outflow, 0, wallet balance)` — with one `debit Wallet, credit Bonus` entry under a fixed idempotency key, which spend reads exclude as a rebalancing rather than a charge.
- One entry has many postings. Each posting sits in the settled or the pending layer, and the entry must balance within each layer.
- The Merkle log's leaves are the entries' content hashes.
